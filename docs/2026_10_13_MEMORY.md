# A soul's memory in ravel

ravel keeps a soul's memory with optmem, ravel's adaptation of
[OptMem](https://github.com/VictorTaelin/OptMem), the memory architecture by
Victor Taelin. It follows OptMem's algorithm as closely as ravel can and
stores the result as a graph beside the soul's transcripts. It is the first
section of the soul's biography (`ravel biography`). This page covers what the memory is, how to read
it, how to build it from a soul's past, and how to check that it is right.

## What the memory is

**Notes.** A note is one line of at most 280 bytes, written whenever the soul
learns something new or something worth keeping happens. In OptMem's words,
that covers:

- a task worth real effort;
- a fact or insight the human teaches;
- anything learned about the human's life, even indirectly;
- any event of lasting effect.

The soul does not note what it already holds. Notes are kept in the order they
were written. A note's place in that order is its identity: `#0`, `#1`, `#2`,
and so on.

**Merges.** Neighbouring notes are merged into one line, then neighbouring
merges, all the way up a binary tree:

- `#0-1` merges notes 0 and 1, and `#2-3` merges notes 2 and 3.
- `#0-3` merges those two, `#0-7` merges two of those, and so on.

Neighbours are always merged by position, never grouped by topic or by date.
A block of up to 16 notes is merged from the notes themselves; a bigger block
is merged from its two halves. A merge is made as soon as its notes exist,
with OptMem's instruction word for word: *Compress memories into one line of
at most 280 bytes. Keep what has lasting effect, drop what does not. Invent
nothing.*

**Wake.** When the soul starts, it reads its whole memory in at most 96 lines.
Recent notes are shown word for word, and older ones through their merges.
OptMem chooses the lines so that detail fades with age.

**The graph.** Every note and every merge is a `ravel:Memory` node in the
soul's store, in the named graph `https://repolex.ai/ravel/NamedGraph/memory-v1`.
A note is linked to each conversation turn it rests on, and a merge is linked
to its two halves. Every link uses the one property Subtexture uses
everywhere, `git-lex:relatedToId`. From any line you can walk down to the
words that were actually said.

## Reading it

```sh
ravel biography         # the whole story at wake; optmem's index is its section
ravel optmem wake           # optmem's index alone: only to get your bearings again
ravel optmem open 16-31     # a merge, opened into its two halves
ravel optmem open '#12'     # a note, with the turns it rests on
ravel optmem recall pool door   # one term across the whole history
ravel optmem check          # optmem checked end to end; exit 1 on any failure
```

`recall` is for what the wake has compressed away. It matches a whole word or
phrase, ignoring case, and prints how often the term was said and when, how
often it was noted and in which months, the highest merge that still names it,
and the latest five notes, with ids that `open` takes:

```
«pool door»: said in 194 turns, 2026-06-17 to 2026-10-14
  noted 17 times: 2026-06 14 · 2026-07 3
  highest merge naming it: #0-2047 … Pool Door has 5 unauth /queue/* writes …
  #2383 2026-07-12 22:11 Rob (07-12): set Pool Door aside. …
```

The lines follow OptMem's format: `#12 2026-04-04 text` for a note, and
`#16-31 2026-04-03..04-08 text` for a merge. The date span (first note to last)
is ravel's one addition to the display, so an old fact does not read as
current. What the soul is shown when it wakes is OptMem's format exactly.

## How it stays up to date

raveld writes every soul's memory itself. You turn it on once, in
`~/.config/ravel/config.yml`:

```yaml
memory:
  writer: claude-code        # the harness whose command line writes the memory
  model: claude-haiku-5-5    # optional; this is the default
```

Without this block, raveld calls no model. It shows the memory that is there
and writes nothing.

With it, raveld looks at every soul every ten minutes. For each soul whose
transcripts gained turns, it:

1. Reads the turns the memory has not read yet, from Claude Code, Antigravity
   and the Claude desktop app, as one timeline in time order.
2. Leaves anything younger than 30 minutes for later, so a conversation still
   going on is not noted halfway through.
3. Waits until the rest fills a stretch, about 24,000 characters of
   conversation, or until its oldest turn is six hours old.
4. Wakes the soul with its memory as it stands, then notes what the soul would
   have noted.
5. Makes every merge that came due, with OptMem's prompt plus one paragraph
   of ravel's (below).
6. Rebuilds any merge the checks refuse, together with every merge above it.

The writer is told it is the soul. It is given the soul's name and its
SOUL.md, and it makes its own merges, as OptMem's agent does.

The first pass for a soul catches up its whole past, the same way. That is how
every soul's memory was first built: 38,537 notes across 20 souls, October
2026. One soul gets at most 60 model calls per pass, so a long catch-up never
holds the others back; it carries on in the next pass.

**It runs on your subscription.** The writer is the harness's own command
line, run with no tools, no settings and no project. For Claude Code that is
`claude -p`. The API key is removed from its environment, and a call that used
one anyway is refused.

**When the subscription is out of allowance**, every soul waits 30 minutes,
and `ravel` shows the memory as paused. A soul whose pass fails for any other
reason waits an hour. `ravel status` shows the reason.

**What it costs.** Measured on Haiku 5.5 while building the first memories:

- About 40 stretches an hour.
- The input is mostly re-read from cache: 11.4 million tokens for 41
  stretches of 4RX's busiest day.

Each soul's `usage.tsv` records the tokens of every call.

### Merges read as a story

OptMem's own merge prompt turned a year of a soul's life into commandments.
The top line of spaceGOAT's memory read "Verify; 'I don't know' if
unverified; no invented fallbacks; …", and named not one
project. ravel adds one paragraph to the merge prompt:

> Write it as what happened: what was worked on, what was discussed, and
> where it stood at the end. Name the projects the lines name. Keep who did
> each thing. Say once which work was unrun or unverified, attached to that
> work, never to a result someone reported working. Never turn a rule into
> something that happened.

It came out of three rounds on spaceGOAT's first 1,024 notes. Each round,
Kira judged all 103 broad and sampled merges blind against their own sources:

| Wording | Claims the sources don't support | Important things dropped |
|---|---|---|
| OptMem's own | 3 | 106 |
| first story wording | turned rules into events, invented cause and effect | — |
| second | 11 | 73 |
| third (shipped) | 7 | 72 |

The story merges drop about a third less, and name the projects, people and
dates. They also say a few more things the sources don't. Every line can be
checked against what it was built from with `ravel optmem open`.

Rules a soul must always keep don't belong in a merge, which is built to lose
detail. They belong in the soul's own documents.

Every merge records which wording wrote it. Add `reword:` under `memory:` and
raveld rewrites the merges written in an older wording, smallest first, up to
40 per soul per pass, after any new turns:

```yaml
memory:
  writer: claude-code
  reword: on          # or off (the default), or a list of soul names
```

### Other harnesses

ravel does not need Claude. A harness can write memory when its command line
can do five things:

1. answer one prompt and exit, with no one at the keyboard;
2. answer in JSON that follows a schema;
3. run on the user's own login, not an API key;
4. run with no tools, no project instructions and no hooks;
5. keep its own session files out of the folders ravel reads transcripts from.

Claude Code is built. Codex, Gemini CLI, Antigravity and Hermes are named: set
one as `writer:` and raveld refuses by name, saying what that harness still
needs. The list lives in `src/writer.rs`.

### What the writer is shown

Only the soul's own life is shown:

- what the soul said;
- what its human said, labelled by name (set `human: Rob` in
  `~/.config/ravel/config.yml`);
- messages from other souls, labelled with the sender's name.

Left out:

- tool calls and their output;
- private thinking;
- compaction summaries;
- the transcripts of subagents and workflows. In OptMem a subagent never writes
  memory, because its notes would arrive duplicated and wrong;
- harness records that arrive as if typed by the human: background-task
  notices, slash commands and their output, system reminders, skill bodies,
  and interruption markers.

A message another soul sends through herdr arrives as plain input, with no
mark on it. ravel finds who sent it from the sender's own transcript: the
`herdr agent prompt` command that sent it, matched by text and time. The
possible senders are the other souls in `config.yml`. When herdr types a
message in while the human is typing, the turn is labelled as both.

## Checking it: `ravel optmem check`

```sh
ravel optmem check           # this soul
ravel optmem check 9bdf2a    # another, by id or path
```

It checks a memory end to end, and exits with status 1 on any failure:

- every note and merge is one line within 280 bytes;
- every merge that is due has been made;
- every note cites turns from the soul's own stream;
- the wake is exactly OptMem's choice of lines;
- the graph loads, and every link from a merge lands on a node;
- every cited turn exists as a Turn in the soul's store.

The match with OptMem itself is tested in `tests/optmem_conformance.rs`. The
test runs OptMem's own program beside ravel and requires the same bytes for
every merge prompt and every wake:

```sh
OPTMEM_MEMO=~/repos/VictorTaelin/OptMem/memo \
  cargo test --release --test optmem_conformance -- --ignored
```

## Which model spoke each turn

Every turn in a soul's store records the model behind it, so you can ask which
model a soul was running on any day:

- `ravel:model` is the model a Claude Code reply reports. The API writes it on
  every reply, so it is the model that actually answered.
- `ravel:modelSetting` is Antigravity's model setting. Antigravity does not name
  a model on its replies; it announces each change of setting, and ravel carries
  the last one forward through the conversation.
- Claude desktop history names no model, so those turns have neither.

```sparql
PREFIX ravel: <https://repolex.ai/ontology/ravel/>
SELECT ?model (COUNT(?t) AS ?turns) (MIN(?ts) AS ?first) (MAX(?ts) AS ?last)
WHERE { GRAPH ?g { ?t ravel:timestamp ?ts .
  { ?t ravel:model ?model } UNION { ?t ravel:modelSetting ?model } } }
GROUP BY ?model ORDER BY ?first
```

## Where it lives

```
<soul>/.ravel/_ignore/optmem/
  memories.jsonl    the notes, in order: OptMem's log
  summaries.jsonl   the merges, one per line, keyed like `16-31`: OptMem's tree
  extracted.tsv     the turns already read
  dropped.tsv       anything refused, and why
  stream.json       how many turns the stream held at the last pass
  usage.tsv         tokens used by each model call
```

On each pass raveld also projects every soul's memory into the graph, where
`ravel biography`, `ravel optmem`, `ravel query` and the UI read it.
